# 청중 포지셔닝 (SSOT) — 우리는 누구를 위한 것인가

> 이 문서는 이 커리큘럼의 **제1원인(first cause)**이다. "어떻게(how)"는 [`큐잉/초보감사.md`](큐잉/초보감사.md)가, **"누구를·왜(who·why)"**는 여기가 정한다. 설계 결정이 흔들릴 때 여기로 돌아온다.

## 결정 (한 줄)
**타깃 = 비전공 실무자** — *일은 하고 있지만(코드를 짜지만) 정규 CS 배경이 없어 기초가 빈, 복붙·감(cargo-cult)으로 굴러온 사람.*

완전 초심자(코드 0)도 배제하진 않지만 **최적 대상은 아니다**. 전공자·시니어는 대상이 아니다.

## 왜 이 청중인가 — gap × scar 이중 필요
이 커리큘럼의 핵심 도구(메모리 모델 = **notional machine**, 식 축약, 스택/클로저 시각화)의 효용은 **두 조건을 동시에 가진 사람**에게서 극대화된다:

- **gap-fill (기초 채움)** — 정규 교육을 안 거쳐 밑바닥이 비어 있음 → "기초를 제로부터"가 무례하지 않고 딱 필요.
- **scar-heal (오개념 교정)** — 이미 짜다가 버그로 데어봄 → 참조 공유·불변성·coercion·클로저가 **"내가 왜 야근했는지"의 카타르시스**.

| | gap-fill | scar-heal | 결과 |
|---|---|---|---|
| 완전 초심자 | ✅ | ❌ (앵커할 경험 없음) | 깊이가 조기 과부하 |
| **비전공 실무자** | ✅ | ✅ | **유일하게 둘 다 → 최적** |
| 전공자·시니어 | ❌ (이미 보유) | 일부 | 깊이가 잉여 |

→ **모든 설계 결정의 정렬 질문**: *"이건 우리 청중의 gap을 채우나, scar를 치유하나?"* 둘 다 아니면 재고한다.

## 청중 후보 × 효용 (별 5개, 실제 커리큘럼 기준)
| 청중 | 효용 | 동인 |
|---|---|---|
| **비전공 실무자 (일은 하지만 기초 없음)** | ★★★★★ | gap + scar 둘 다 |
| 부트캠프 수료 주니어 | ★★★★☆ | scar 강함, gap 일부 |
| 프레임워크 사용자(React/Vue)·비전공 | ★★★★☆ | 참조·불변성=state 버그 원인 (payoff 링크 있으면 ★5) |
| 코딩 교육자·멘토 | ★★★★☆ | 자기학습 아닌 **교보재**로 |
| 완전 초심자 (코드 0) | ★★★☆☆ | gap만, scar 없음 → 깊이 조기 과부하 |
| CS 전공 학생·개발자 | ★★☆☆☆ | gap 없음 → 깊이 잉여 |
| 비개발 교양(안 짤 사람) | ★★☆☆☆ | 드릴·실코드 과함 |

## 프레이밍 규칙 (오독 금지)
- **"완전 제로/제로부터" = 커리큘럼의 출발점**(기초를 밑바닥부터 다진다)이지, **학습자가 초보라는 뜻이 아니다.** 코드를 짜는 실무자가 "나한텐 너무 기초겠네" 하고 이탈하지 않게, "제로"는 항상 *가르치는 내용의 시작점*으로 표현한다.
- **자기선별은 포함 + 솔직한 배제로.** 누구에게 안 맞는지 말하는 게 신뢰를 높이고, 안 맞는 독자를 초반에 걸러 나쁜 인상 이탈을 막는다. (홈 '🧭 이 강의, 나에게 맞나' 핏 체크 블럭 = 이 문서의 학습자용 투영.)
- **내부(이 문서)=근거(전체 별점표) · 외부(홈 핏체크)=거울(그 독자용 fit/not-fit).** 별점 순위표는 학습자에게 노출하지 않는다.

## 실무 payoff 레이어 (진행 원칙)
프레임워크 사용자·실무자의 scar를 더 세게 건드리려면, **완전 초심자를 안 다치게** progressive disclosure(muted 심화 톤)로 **선택적 payoff 링크**를 얹는다. 예: M4-2(참조 공유) 끝에 *"💡 실무에서 — 이게 React state를 `...spread`로 복사해야 하는 이유"*. 커리큘럼의 축을 프레임워크 버그로 바꾸지는 않는다(그건 다른 제품).
